## [2026-08-01] lint | Retrieval and validation fixes for multi-hop join questions

- Paths touched: sql_query_agent.py, wiki_agent.py, db_introspect.py, wiki/index.md
- Root-caused two failed queries: "ship point address for SUPC-600006" (agent said the data didn't exist) and "shipping address for vendor V00999" (agent invented a `suppliers` table, then invented a `vendor_storage_type` column on `source_vendors`).
- Cause 1 — index.md's entity one-liners were all the same boilerplate ("Postgres table `X`, documented from live schema + sample data."), giving the navigation LLM no real content to match a question's meaning against, only the table name string. Fixed `update_index()` in `wiki_agent.py` to render each entity's real first Overview sentence instead (e.g. `vendor_shipping_points` now surfaces "...associating vendors with their respective shipping points and addresses"); applied the same fix directly to the live `wiki/index.md` so it takes effect immediately, ahead of the next full `run_agent()` pass.
- Cause 2 — `generate_sql()` never gave the model the full FK graph, so it couldn't discover a bridge table (e.g. `items -> vendor_pricing -> vendors -> vendor_shipping_points`) it hadn't already been told about by name. Now unconditionally loads `relationships/overview.md` into every request; its `[[entities/...]]` links feed the existing auto-expansion step. Also added `find_multi_hop_chains()` to `wiki_agent.py`, which deterministically finds table pairs with no direct FK and feeds them into `QUERY_PROMPT` as required worked examples for the next `queries/` regeneration.
- Cause 3 (validation gap) — `validate_query_sql()` only checked dotted `table.column` references. A fully invented table (`suppliers`) or an unqualified hallucinated column (`vendor_storage_type` on `source_vendors`) had no prefix to check and passed validation, only failing later at Postgres. Added a FROM/JOIN table-existence check and, for simple single-table/no-join/no-CTE queries, an unqualified-column check — both restricted in scope to avoid false positives on multi-table or subquery SQL.
- Follow-ups: the index-summary fix and the `find_multi_hop_chains` query-generation change haven't been exercised through a live `run_agent()` pass yet (needs Ollama + Postgres reachable) — worth a full regeneration + re-test of both failing questions once available.
